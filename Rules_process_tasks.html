Выберите роль сверху — увидите подробный алгоритм. Если в роли есть сквозные действия — они выполняются на всём протяжении задачи. Альтернативные шаги — только при выполнении условия.

Карточки ролей

📋
РП / Аналитик
Владелец родительской задачи
Когда: получена задача; взятие в работу; изменён функционал
  • Создаёт родительскую и дочерние по направлениям
  • Заполняет оценки, связи, направление для F/B
  • Релиз, спринт, даты
🎨
Дизайнер
Направление Design
Когда: назначена Design-задача
  • Проверяет/проставляет оценку
  • Выполняет дизайн по ТЗ
  • Списывает трудозатраты → закрывает
🔍
Аналитик-исполнитель
Направление Analytics
Когда: назначена Analytics-задача
  • Списывает трудозатраты перед ревью
  • Ревью ТЗ: «Ответственный за ревью», чат, встреча
  • Корректировки ТЗ: правки → повторное согласование
🖥
Front-разработчик
Направление Front
Когда: назначена Front-задача (Улучшение или Ошибка)
  • Оценка, Направление = FRONT
  • Перед передачей на ревью: трудозатраты + статус Улучшения Проверка кода
  • Для Ошибки — Развернута на тесте (контур)
  • Закрытие: Улучшение — Лид, Ошибка — Тест
⚙️
Back-разработчик
Направление Back
Когда: назначена Back-задача (Улучшение или Ошибка)
  • Оценка, Направление = BACK
  • Перед передачей на ревью: трудозатраты + статус Улучшения Проверка кода
  • Для Ошибки — Развернута на тесте (контур)
  • Закрытие: Улучшение — Лид, Ошибка — Тест
🧪
Тестировщик
Test · 3 контура + тест-кейсы
Когда: после ТЗ → тест-кейсы; DEV/STAGE/PROD → тесты; Ошибки → закрывает
  • Пишет тест-кейсы в описании тест-задачи
  • DEV → «Протестировано на DEV»
  • Ошибки: закрывает после проверки
📝
Технический писатель
Работа по полю «Документация»
Когда: есть задачи с «требует корректировок»
  • Отчёт в Redmine по фильтру
  • Правки, прикрепляет к задаче + Confluence
  • «изменения внесены»
📢
СТП
Служба технической поддержки
Когда: после «Регресс завершен» — задачи готовы к PROD
  • Сообщение в чате о техработах
  • Публикацию не выполняет
  • Релиз-ноут, письмо, уведомление в чате
👤
Лид / зам направления
Ревью + публикация + закрытие Улучшений
Когда: ревью ТЗ; проверка кода; публикация; закрытие Улучшений
  • Улучшение: ревью → «Решена» → DEV → закрыть
  • Ошибка: ревью → контур (не закрывать — закроет Тест)
  • Публикация на STAGE и PROD

Общие принципы

  • 1
    Все задачи — в проекте исполнителя. Родительская: Структура, Backlog, релиз Backlog. Инициатор — РП (от заказчика) или Лид/зам.
  • 2
    Дочерние задачи — свой трекер по направлению. Статус Backlog. Тип: Улучшение или Ошибка.
  • 3
    Взятие в работу: трекер не меняется, статус Новая/В работе, задача переводится в актуальный релиз и спринт, ставятся Дата начала и Срок завершения.
  • 4
    Оценка временных затрат (с риском +20 %) — обязательна. Исполнитель при получении задачи проверяет и проставляет оценку, если не заполнена.
  • 5
    Ревью обязательно: аналитика — ревью ТЗ; Front/Back — проверка кода Лидом. Публикация на DEV — только Лид/зам.
  • 6
    Жизненный путь меток: Развернута на DEV → Протестировано на DEV → Регресс → Регресс завершен → Смоук → Смоук проведен.
  • 7
    Публикацию на любой контур выполняет только Лид направления или его зам. Разработчик, тестировщик, СТП не публикуют.
  • 8
    СТП оповещается только перед PROD (после «Регресс завершен»). На DEV и STAGE — оповещения нет.
  • 9
    WORKFLOW «Ошибка» (баг):
    • Разработчик завершил фикс → сам ставит Развернута на тесте (контур).
    • Лид/зам — проверяет код и публикует на контур, но не закрывает.
    • Тестировщик — закрывает задачу после проверки на контуре.
  • 10
    WORKFLOW «Улучшение» (новая функциональность):
    • Разработчик завершил работу. Перед передачей на ревью проверяет списание трудозатрат и ставит Проверка кода.
    • Лид/зам — проводит ревью кода. После успешного ревью ставит Решена.
    • Лид/зам — публикует на DEV + метка и закрывает задачу.
  • 11
    Баги при тестировании создаются только как дочерние задачи своей тест-задачи. Статус — Новая. Обязательно: приоритет, критичность, исполнитель.
  • 12
    Hotfix (срочные баги): отдельный релиз, только нужные задачи, тот же workflow, срочно.
  • 13
    Документация: если функционал изменён — аналитик у родительской ставит требует корректировок. Тех.пис: отчёт → правки → прикрепить к задаче + Confluence → изменения внесены.
  • 14
    Связи: дочерняя → родительская (Parent / Child); только родительская → задача заказчика.
  • 15
    Направление — только Front / Back. Для Front/Back поле заполняется обязательно.
  • 16
    Наименование: ФБ. Стори. Направление.
  • 17
    Трудозатраты обязательны до ревью: перед передачей на ревью исполнитель проверяет списание трудозатрат. Без них задачу закрыть невозможно.
  • 18
    Тест-кейсы: после согласования ТЗ тестировщик пишет тест-кейсы в описании тест-задачи — параллельно с разработкой.

Оценка временных затрат

📌
Поле «Оценка временных затрат». Риск +20 %. В часах и днях (1 день = 8 ч).

Родительская задача

  • 1
    В поле — общая оценка с риском +20 %.
  • 2
    В описании — разбивка по направлениям.

Дочерние задачи

  • 1
    Оценка по направлению — с риском +20 %.
  • 2
    Соответствует разбивке в родительской.
  • 3
    При изменении — обновить в родительской и в описании.
  • 4
    Исполнитель любого направления при получении задачи проверяет и при необходимости проставляет оценку по своему направлению.
Σ Калькулятор риск +20 %
Designс риском: 9.6 ч.
Analyticsс риском: 9.6 ч.
Frontс риском: 14.4 ч.
Backс риском: 14.4 ч.
Testс риском: 9.6 ч.
Общая оценка с риском +20 %
57.6 ч. ≈ 7.2 дн.
1 день = 8 ч

7.3. Проверка кода — два workflow

      

        ⚠️
        
Workflow отличается для трекера «Улучшение» и «Ошибка» — как по статусу, так и по тому, кто закрывает задачу.

      


      
A. Улучшение (новая функциональность)

      

        

          1
          
Перед передачей на ревью

          
Разработчик списывает трудозатраты и ставит статус Проверка кода.

        

        
→

        

          2
          
Лид/зам: ревью

          
Проводит ревью кода. При замечаниях — вернуть разработчику.

        

        
→

        

          3
          
«Решена» после ревью

          
После успешного ревью Лид/зам ставит Решена.

        

        
→

        

          4
          
DEV + метка + закрытие

          
Лид/зам публикует на DEV, ставит метку и закрывает задачу.

        

      


      
B. Ошибка (баг)

      

        

          1
          
Списать трудозатраты

          
Разработчик проверяет списание.

        

        
→

        

          2
          
Статус «Развернута на тесте (контур)»

          
Разработчик сам выставляет Развернута на тесте (контур).

        

        
→

        

          3
          
Лид/зам: ревью + публикация

          
Проверяет код → публикует на контур. Задачу не закрывает.

        

        
→

        

          4
          
Тестировщик закрывает

          
После проверки исправления тестировщик закрывает задачу Ошибки.

        

      


      

        🚫
        
Ключевое отличие: «Улучшение» — разработчик ставит «Проверка кода» → Лид ставит «Решена» после ревью → публикация → закрывает Лид/зам. «Ошибка» — разработчик ставит «Развернута на тесте (контур)» → публикация → закрывает тестировщик.

→

        

          3
          
Метка

          
После успеха: Протестировано на DEV.

После «Смоук проведен» — СТП формирует релиз-ноут, письмо о завершении + уведомление в чате с пользователями.

      


      
7.7. Регистрация багов

11
Краткая памятка

      

        
ТРЕКЕР
Родительская — Структура. Дочерние — свой по направлению. Не меняется.

        
СТАТУСЫ
При создании — Backlog. После взятия — Новая/В работе. Улучшение: Проверка кода → Решена (после ревью). Ошибка: Развернута на тесте (контур).

        
ЗАКРЫТИЕ
Улучшение: закрывает Лид/зам после публикации. Ошибка: закрывает тестировщик после проверки.

        
ТРУДОЗАТРАТЫ
Перед ревью исполнитель проверяет списание трудозатрат. Без них задачу закрыть нельзя.

        
ТЕСТ-КЕЙСЫ
Пишутся тестировщиком в описании тест-задачи после согласования ТЗ.

        
КОРРЕКТИРОВКИ ТЗ
Если после встречи нужны правки — правки → повторное оповещение → повторная встреча → согласование.

        
ПУБЛИКАЦИЯ
Только Лид/зам. Разработчик, тестировщик, СТП не публикуют.

        
МЕТКИ

          Развернута на DEV (Лид) →
          Протестировано на DEV (Test) →
          Регресс (Test) →
          Регресс завершен (Test) →
          Смоук (Test) →
          Смоук проведен (Test).
        

        
ОПОВЕЩЕНИЕ СТП
Только перед PROD. СТП публикацию не выполняет.

        
РЕЛИЗ · СПРИНТ
При создании — Backlog. После взятия — актуальный релиз и спринт. Hotfix — отдельный hotfix-релиз.

        
ДАТЫ
После взятия — Дата начала + Срок завершения. Раньше — фактическая дата.

        
НАПРАВЛЕНИЕ
Для Front/Back — обязательно.

        
ОЦЕНКА
«Оценка временных затрат», риск +20 %. Исполнитель обязан проверить/проставить.

        
РЕВЬЮ ТЗ
Аналитик → «Ответственный за ревью» (все лиды) → чат → встреча → согласование.

        
БАГИ
Только дочерние тест-задачи. Статус Новая. Приоритет + критичность + исполнитель.

        
СТП
Оповещается после «Регресс завершен». Готовит сообщение и релиз-ноут. Публикацию не выполняет.

        
HOTFIX
Отдельный релиз, тот же workflow с метками, срочно.

        
ДОКУМЕНТАЦИЯ
Аналитик ставит требует корректировок. Тех.пис: отчёт → правки → прикрепление к задаче + Confluence → изменения внесены.

        
СВЯЗЬ
С заказчиком — только у родительской.

        
ИМЯ
ФБ. Стори. Направление.
